    The Getozvea project,
    explained from the ground up.

    A structured record of the problem, research, design decisions, implementation, testing, deployment considerations, and lessons behind this full-stack website and content management system.

    AuthorGeorge Mwaura Mungai

    Abstract

    Getozvea is a full-stack website and content management system built for a web design and digital studio. It responds to a practical problem faced by small businesses: needing a site that looks professional and performs well, while still being easy for the owner to update without depending on a developer for every small change.

    The result combines a public marketing website with a secure, purpose-built admin panel. An administrator can edit text, manage services and portfolio entries, upload images, update contact information, and review contact form messages. This report explains the reasoning behind the system rather than reproducing its source code.

    Chapter 1

    Introduction

    A studio's own website is both a marketing tool and a proof of its capability. A slow, dated, or difficult-to-update website can undermine trust before a conversation begins. Getozvea was conceived as a site that communicates quality while giving its owner control over everyday content changes.

    Aim

    Design, build, and document a complete website and content management solution for a fictional web design studio.

    Objectives

    Create a distinctive public site, a working backend, authenticated administration, image uploads, contact handling, and a tested result.

    Scope

    One site with home, services, portfolio, about, contact, and supporting admin tools. No multi-tenant platform, payments, visitor accounts, or advanced analytics.

    Significance

    Demonstrates end-to-end ability: translating a business problem into requirements, architecture, implementation, testing, evaluation, and documentation.

    Chapter 2

    Literature review and background research

    Websites are important trust and decision-making touchpoints for small service businesses. A content management system separates editable content from presentation, allowing a non-technical owner to update a site without editing code.

    General platforms such as WordPress provide breadth and a large ecosystem, but also introduce plugin maintenance, database configuration, and a wider security burden. Headless services offer flexibility but create external dependencies and possible subscription costs. Static sites are fast and simple, but often require a rebuild for each change.

    For a single site with a small, stable set of content types, a bespoke backend and focused admin interface offered the best fit: control over the experience, no third-party subscription, and only the features the owner actually needs.

    Chapter 3

    Research methodology and workflow

    Development followed an iterative, incremental approach. The public visual design was established first, then the backend, dynamic content, and admin panel were built around a concrete layout rather than abstract assumptions.

    01DefineProblem, audience, scope, and requirements.
    02DesignArchitecture, interface, content structure, and flows.
    03BuildImplement in small, verifiable slices.
    04TestCheck features, integrations, usability, and security.
    05DocumentRecord decisions, limitations, and future work.
    Chapter 4

    Requirements analysis

    Public visitor

    Browse the studio, review services and work, understand the offer, and submit an enquiry through a clear contact form.

    Business owner

    Log in securely, edit text, manage services and portfolio items, upload images, update contact details, and review messages.

    Maintainer

    Work with clear modules and simple storage so future structural changes remain understandable and affordable to deploy.

    Quality requirements

    Usable without coding knowledge, reasonably secure, responsive, maintainable, fast enough for ordinary connections, and deployable on modest hosting.

    Chapter 5

    System design and architecture

    The system uses three cooperating parts: a public frontend, an administrative frontend, and a shared Node.js and Express backend. Both frontends communicate with the backend through a defined request-and-response interface, while the backend acts as the single source of truth for all editable content.

    Public frontendReads current content and renders the live site.
    Admin frontendAuthenticates the owner and sends content changes.
    Backend APIHandles content, sessions, uploads, and messages.
    Structured data storeStores hero, services, portfolio, about, contact, footer, and submissions.

    A file-based store was chosen because the content volume is modest and relationships are simple. It keeps deployment, backup, and recovery straightforward, while its limitation is explicit: concurrent multi-user editing would justify a proper database migration.

    Chapter 6

    Interface and user experience

    The public interface avoids interchangeable template patterns by using a deliberate palette, serif display type, geometric sans text, and a consistent rhythm of headings, supporting copy, and content grids. The admin interface prioritises clarity and predictable controls over visual flourish.

    Information architecture

    A single public page is organised around home, services, portfolio, about, and contact. Admin areas mirror those content groups.

    Responsive design

    Desktop grids collapse for smaller screens, navigation adapts, and forms remain usable on mobile devices.

    Accessibility

    Semantic headings, visible focus states, descriptive form labels, and intentional contrast support keyboard and assistive technology users.

    Admin experience

    Plain-language labels, immediate save feedback, confirmation for destructive actions, and simple image selection reduce friction.

    Chapter 7

    Implementation overview

    The frontend keeps structure, styling, and content population separate. A page shell requests current content and fills predefined placeholders, building services and portfolio grids from the returned data rather than assuming a fixed number of entries.

    Backend routes are grouped by responsibility: public reads, authenticated writes, uploads, authentication, and contact submissions. Focused modules centralise data access and authentication checks, making the system easier to test and change.

    Security baselineHashed passwords, session-based access control, time-limited sessions, restricted image types, generated filenames, and escaped user-supplied text.
    Chapter 8

    Testing and quality assurance

    Unit checks

    Authentication, validation, and data read/write logic with expected and edge-case inputs.

    Integration checks

    Login sessions, content changes, image retrieval, and contact submissions across complete request cycles.

    User acceptance

    Realistic admin tasks such as changing a headline, adding a portfolio item, deleting a service, and reviewing a message.

    Security checks

    Rejected unauthenticated writes, invalid credentials, upload restrictions, and safe rendering of submitted text.

    Performance

    Practical observation of page load, admin saves, and realistic image uploads at the intended scale.

    Regression

    Previously verified features rechecked after shared data or authentication changes.

    Chapter 9

    Deployment and operations

    The system is designed to deploy as one unit to a host running a modern server-side JavaScript runtime. The critical hosting requirement is persistent file storage because content and uploaded images live on disk. Serverless or temporary filesystems require external storage before deployment.

    Maintenance

    Keep runtime dependencies updated, confirm the service remains reachable, and review stored messages regularly.

    Backups

    Copy the structured data file and uploads folder to a separate safe location on a recurring schedule.

    Recovery

    Restore the data file and uploads directory; no separate database state needs reconciliation.

    Scaling

    Move to a database, stronger monitoring, and external media storage if traffic, content volume, or editor count grows.

    Chapters 10–14

    Challenges, evaluation, risks, and conclusion

    The main technical challenge was keeping the data model, backend routes, and frontend rendering synchronised as new fields were introduced. Treating the data structure as the authoritative definition and rechecking dependent features reduced regressions. Image uploads also needed to be persisted with the relevant entry rather than merely returning a file reference.

    Design iteration revealed that familiar agency patterns could weaken the project's claim to distinctive design. The admin panel also became clearer after long, undifferentiated forms were split into focused content areas. Time was managed by keeping the scope narrow and deferring multi-language support, granular permissions, and advanced analytics.

    Within its stated scope, the system met its objectives: it has a distinctive public interface, a working backend, authenticated content management, image handling, persistent contact submissions, and a documented testing approach. Its deliberate limitations are the single-admin model, file-based storage, and baseline rather than full professional security hardening.

    Recommended future workDatabase migration, role-based permissions, multilingual content, analytics, draft and publish workflows, login rate limiting, and a formal security review.

    Log in, choose a content area, edit the labelled fields, save, and confirm the public site reflects the change. Add portfolio projects with a title, description, and image. Review contact enquiries in the messages area, and log out on shared devices.
